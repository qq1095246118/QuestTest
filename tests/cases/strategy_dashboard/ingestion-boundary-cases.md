# 分润平台：基础数据接入可控数据场景

本文件补充 SD-101～SD-120 的输入变体，保留原主用例编号和中文标题。当前共 38 个数据子场景，均为 **DESIGNED_NOT_INJECTED（已设计，尚未注入被测平台）**。它们不作为新的 38 条独立主用例，也不计入真实业务通过数。

## 范围

只验证分润平台取得上游结果后，字段是否保留、事实是否去重、账户/策略/订单是否正确关联、状态更新是否正确，以及读取失败是否被误报为完整成功。页面格式化、复杂指标公式、告警、分润锁单、收款和清算均不在本批变体范围。已有 SD-103 的页面精度检查继续保留，本批原值精度检查归到 SD-101。

原有 20 条用例已写到负值、未知状态、空仓等边界，但没有可重复投递的具体输入。本次增加的是这些场景的可控数据和顺序，不把已有业务意图重复登记为新增主用例。

## 数据文件和解释

数据在 [ingestion_boundaries.json](../../data/strategy_dashboard/ingestion_boundaries.json)。每个子场景包括：

- `fixture_id`：稳定子场景编号；`parent_case_id`：对应原主用例。
- `source_responses`：平台上游读取边界按顺序返回的数据。多项表示多次同步或多页读取，必须实际让接入流程消费，不能只重复 GET。
- `expected`：独立写出的平台输出应满足的字段、集合、数量或业务断言。
- `required_contract`：执行前需要从正式接口/字段定义确认的条件；这些未确认时不能擅自固定规则。
- `execution_status`：设计进度，不是执行结果。真实执行结果应另存报告，不反写为静态数据通过。

数据中的账户、策略、订单、事件标识均为合成值；时间固定在 2026-09-20，测试时钟为 10:02 UTC。金额使用十进制字符串，防止测试数据自身在构造时丢失精度。最终字段类型、单位和允许精度必须映射到实际源契约；逻辑字段名不声称是现有 API 字段。

同一源事件的业务身份应使用真实来源定义的复合键。不能假定所有事件 ID 全局唯一，也不能强行要求本来全局唯一的 ID 在两个账户下重用。SD-110-CROSS-ACCOUNT 需要先确认来源身份作用域。

## 注入位置与执行顺序

有效链路是：**合成上游输入 → 分润平台真实接入/同步流程 → 平台查询结果 → 独立预期断言**。

可以在隔离测试部署替换平台读取的上游响应，或向平台实际消费的测试暂存数据中写入受控记录。不能直接写最终查询结果表来证明接入正确，也不能在 pytest 内同时模拟输入和平台输出后宣布业务通过。

截至本次只读检查，测试 Backend 的公开 OpenAPI 未声明可提交任意合成账户/持仓/成交记录的 fixture 注入接口。已公开的历史回补接口使用真实交易所数据，不是本数据集的导入接口。公开文档未列出不代表内部能力一定不存在；当前尚未确认实际注入点，故没有写测试库、调用回补或触发业务变更。

每个子场景按以下顺序执行：

1. 为本次运行分配唯一资源前缀，统一替换全部账户、策略、事件和关系引用；确认逻辑字段到实际源字段及查询字段的映射。
2. 准备该场景自己的基线。需要分阶段的场景按 `source_responses` 顺序投递，每阶段等待真实接入完成后再继续；分页响应只作为同一轮读取中的不同页。
3. 查询平台对应结果，保存实际消费阶段、查询范围、原始字段、集合和状态。去重场景还需读取完整明细，不能仅查聚合值或当前第一页。
4. 使用 `expected` 中的独立预期核对平台结果，金额按实际字段精度比较，身份按完整命名空间比较。缺接入路径、缺契约、准备失败分别报告，不能用本地结构通过替代业务结果。
5. 清理或恢复本次创建且能确认归属的测试资源。每条场景使用自己的隔离数据，其他场景不能继承其缺失状态、关系或事件。

若缺失值处理允许返回最后一次值，必须保留其旧时间和不可用/降级状态，不能冒充本次成功获取。不同字段采集时间不一致也不自动等于 Bug；只有正式对齐规则明确时才判定超时差。没有规则时，仅检查公开时间未伪造、缺失未填零、部分结果未标完整。

缺字段或部分来源失败时，先确认实际提交粒度。下列有效部分保留的预期适用于正式的部分成功契约；如果实现按已批准规则整行或整批拒绝，应先改为该契约对应的唯一预期后执行，不能将原子拒绝直接判为 Bug，也不能把相反结果同时判为通过。

## 三个完整执行示例

### 完全相同的源批次重复投递（SD-110-REPLAY）

- 前置：本次测试账户没有 e1/e2，输入包含 e1、e2 两条事件，金额均为 10，时间相同。
- 第一次操作：让真实接入流程消费第一组源响应，查询平台完整明细，应得到 e1/e2 共两条。
- 第二次操作：再次投递同一源批次并完成第二次接入，查询相同范围。
- 期望：最终唯一集合仍是 e1/e2，共两条；不是四条，也不能因为金额和时间相同而被去成一条。
- 失败判断：重复同步后数量增长，或两个不同事件被错误合并，均属于接入去重错误。

### 新快照之后抵达旧快照（SD-101-STALE）

- 前置：确认真实源使用哪个字段确定“当前快照”，是否允许历史修订；未确认不能自行规定按抵达时间或业务时间覆盖。
- 第一次操作：投递 10:01 钱包 1100 的快照并查询平台结果。
- 第二次操作：投递晚抵达的 10:00 钱包 1000 快照，再查询当前和历史结果。
- 期望：若正式规则按 observed_at 选当前值，当前应保持 1100；历史允许保留 1000。无论采用何种正式规则，都不能把 1000 错标为 10:01 的来源值。
- 失败判断：确认选值规则后，当前值错误倒退；或接口公开的金额与来源时间被拼错。

### 多账户来源中只有部分成功（SD-101-PARTIAL-FAILURE）

- 前置：平台本次读取目标为账户 A/B；A 钱包 1000，B 来源读取失败。
- 操作：让真实接入流程读取该批源响应，再查询账户明细与接入完整性字段。
- 期望：A 的已知值保留；B 标识缺失或保留明确标旧的历史值；请求/成功/失败数量按实际接口字段对应 2/1/1。不能把 B 变成“成功取得余额 0”。
- 失败判断：用 A 的钱填到 B、B 失败被记为成功，或该批次被标为完整成功。

## 与已有待补项的对应关系

- SD-101-FIELD-TIMES 与既有 GAP-012 / DATA-122 的字段采集时点部分关联；本次只补具体数据和稳定断言，不表示计数器重置等全部子场景完成。
- SD-101-TRUNCATED 验证一轮读取是否完整；它不能代替 GAP-010 / DATA-121 对运行中、全登记、归档等业务集合的完整覆盖。
- 非 USD 换汇、分润精确资格与告警鲜度属于后续模块，不因本批输入存在币种或时间字段就计作已覆盖。
