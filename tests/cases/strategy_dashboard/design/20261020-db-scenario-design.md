# 2026-10-20 策略管理与分润：数据库造数与实际消费设计

阶段：文档和本地代码审查，尚未执行本轮数据库造数或业务测试。本文补充造数入口与验证边界，不替代原有 264 个检查点，也不将检查点合并为少量“大场景”。

## 结论与依据

可以把数据库造数作为主要场景准备方式。收益正负、资金变化、A→B→A、分钟峰谷、平仓轮次、多账户组合、历史账单等，都可以通过可控事实和前置状态构造。完整验证仍须让待测的计算、后台任务或业务接口实际执行。

例如，测分段收益率时写本金、累计已实现和归属历史，再读真实计算；测达标出账时准备精确资金证据，让正式检测任务生成账单和新周期；测登记到账时准备待收账单，再调用正式登记接口。

本次已阅读[分润系统V2 接口文档](https://jjp1ynw9z1yy.jp.larksuite.com/wiki/DO4hw6LTYiyiXukYyskjkGQcpkf)的调用约定、页面入口、接口速查、示例、全部表分组及缓存排错章节。正文更新日期为 2026-10-20。

本文的N01—N32、E01—E08均为该文档的接口编号，不与需求矩阵中的通知需求N01等编号混用。

文档自身限定：表结构按代码模型整理，未代表已查实际建表/索引；本轮年化门槛补丁尚未部署。因此，本文表名、关系及参数是当前文档契约，实际列名、JSON 路径、后台消费和部署版本仍需在执行器接入时核实。没有把文档中的模型关系写成可直接执行的 SQL。

业务公式继续沿用[需求与检查点矩阵](20261020-coverage-matrix.md)。接口文档说 `quant_strategy_account_runs` 模型支持多策略归属，不单凭该模型描述扩大已确认的“单账户同时单策略”测试范围；账户多段归属、同策略多账户照常覆盖。

## 先区分造数写入的位置

| 写入位置 | 可验证的处理范围 | 需要保留的限制 |
| --- | --- | --- |
| NT PostgreSQL 的归属、原始资金计数器、订单/成交等事实 | 从该事实被真实消费开始，到分段、计算、发布、API及适用页面 | 仍未覆盖交易所/NT 到 PG 的上游归档；一笔成交也不保证自动生成资金累计样本。 |
| `quant_segmented_nt_facts` 或其他采集后的输入 | 从该层开始的计算与后续读取 | 跳过了原始事实采集及投影，单独标明实际覆盖层。 |
| `quant_account_snapshots`、`quant_collection_batches.current_data`、`quant_strategy_performance_samples` | 由这些采样输入进入的查询、聚合或后续处理 | 先证明当前分支消费它们；不能据此宣称 NT 原始事实链已经通过。 |
| `quant_curve_points_minute/rollup`、`quant_segmented_performance_generations` 或已算好的 NAV/回撤 | 已有结果的查询、映射、分页、缓存与展示 | 不能据此证明被直接写入的指标公式。`fact_nav_sample`、`fact_performance_sample` 中也可能含上游计算字段，按字段判断。 |
| 手工 `quant_read_views.payload` | 指定输入的查询计算分支、冻结读取 | 绕过服务正常构建视图和部分事实消费链；读到指定 `snapshot_id` 不等于正式源已消费。 |
| 账单/到账等已完成业务状态 | 已有状态的读取、筛选和页面展示 | 测生成、确认、权限、并发、幂等或通知时，由真实处理程序产生目标状态。 |

“原始”相对于待测逻辑定义：累计已实现是收益率公式的输入，但可能已是逐笔成交聚合的输出。每条用例明确自己验证哪一段。

## 三条主要消费链

### 绩效、归属与风险

```text
NT assignment/migration + 资金与绩效事实
  → quant_segmented_nt_facts / quant_segmented_performance_checkpoints
  → quant_segmented_performance_generations（含 source_generation、封存输入）
  → Redis 已发布计算结果
  → N01 / N02 / N03 / N04 及列表与页面
```

`range_sources` 是 generation 的 payload 内输入片段，不是另一张表。不能从表名猜测任意字段都被当前公式消费。当前页面显式传 `metric_source=prometheus` 是分支名称，实际也使用 NT、MySQL、Redis；不据名称断言所有值都直接来自 Prometheus。

### 展示采集与当前仓位

```text
实际来源的财务、运行和完整持仓证据
  → quant_collection_batches（manifest/current_data）
  → 财务/策略采样、分钟曲线、平仓重放检查点
  → 已发布视图与 Redis
  → 当前指标、仓位、曲线
```

默认后台展示同步为 300 秒，页面默认 10 秒轮询。页面重复读取不会补出新的真实分钟观测。当前分钟仓位在 batch 的 `current_data`；旧 `quant_position_snapshots` 不是当前分钟主路径。

### 账户计费与到账

```text
账户 profile + 有效 policy/cycle + 精确 NT 资金证据
  → 独立 60 秒计费检测
  → 触发快照 + 冻结账单 + 后继周期 + notification outbox
  → N21/N22 查询
  → N23 正式登记到账
  → 原单实收、版本、页面展示基准更新
```

计费按账户，不按每条 run 独立建账；不能因账户有多个历史运行段制造重复应收。计费不等五分钟展示缓存，需分别观察两条链。60 秒是任务周期，不是所有账户完成时限。

## 三个可复核的数据例子

### 分段收益与账户收益分开验证

沿用 `V2-MET-006`：同策略 S 下，账户 X 第一段本金100、已实现增量10；真实追加100后第二段本金200、已实现增量40；账户 Y 本金100、收益0。

- 策略 S：`(10 + 40 + 0) / (100 + 200 + 100) = 12.5%`。
- 账户 X 全历史：`50 / 最新本金200 = 25%`。
- 给同一资金段额外增加采样，策略分母仍为400，不能把快照张数当资金段数。

造数时准备资金/累计计数器和真实段边界；不直接写 `cumulative_return=0.125`。本例验证段与收益率计算，若未投递逐笔成交，不记为成交聚合到累计已实现的验证。

### 分钟峰谷在日展示中保留

沿用 `V2-RISK-002`：固定有效本金1000、未实现0，同一日四个实际分钟观测的已实现累计依次为0、200、−100、100；对应产品净值为1、1.2、0.9、1.1。

- 最大回撤：`(1.2 - 0.9) / 1.2 = 25%`。
- 最后实时回撤：`(1.2 - 1.1) / 1.2 ≈ 8.333333%`。
- `granularity=1d` 控制输出点，不能只拿日末1.1重算而漏掉日内0.9。

将净值列作为独立预期，向被测计算提供实际消费的本金与已实现源序列；不把预期净值、最大回撤写入结果表。若源中存在可直接读取的同名结果字段，还须确认本次命中了产品净值重算分支。

### 出账与到账分别经过真实处理

沿用 `V2-BILL-014/018`、`V2-REC-010/011`：本金100、触发率5%、分润率35%、合格钱包105。让计费任务产生一张应收1.75的账单，触发快照与新周期本金105同事务落库。

之后输入钱包108且无资金划转；旧应收仍1.75，新周期利润为3。指定商务通过N23先登记0.75，再登记1，两次均关联原账单；确认实收依次0.75、1.75，未收依次1、0。到账登记不再次扣钱包，也不把新周期利润3清零。

若只想验证既有已收账单页面，可以直接准备历史收款事实；上述出账、确认、超收防护和副作用则分别由真实任务/API产生。

## 一条造数用例的执行步骤

1. 固定检查点/SUB-ID、测试账户/策略/交易所、原始事件时间线、统计范围和部署/公式版本。先独立确定期望成员、区间、分母及预期值。
2. 校验本次需要的真实列、JSON路径、来源优先级及loader筛选；准备专用身份、映射和关联前置。新一轮事实使用可追踪的稳定身份。
3. 记录源行、水位、已发布版本和首次读取的基线；提交本次数据，使真实消费者能够读取。后台跨连接处理时，不能指望外层未提交事务被消费。
4. 让正常任务消费，或使用已经确认存在的内部重放入口。文档没有给任意重算端点；不臆造接口、不直接篡改checkpoint来制造通过。历史UPDATE未被增量扫描重新发现时，记录实际缺口并核实正式修订/重放机制。
5. 观察实际消费、分段结果和发布。核对各自的generation、source_generation及引用关系；不同流水线代次不要求数字相等。只见updated_at变化不足以证明使用了本次事实。
6. 正常发起新读取，取得服务生成的视图；分页沿用该视图和筛选。需要看新数据时不能持续复用旧冻结snapshot。`Cache-Control: no-cache`不保证服务端Redis重算，不以全局清缓存代替正常失效/发布验证。
7. 断言原始输入对应的独立期望；同时核对对象、范围、源时间、公式、质量状态与发布引用。页面验证另加单位、日显示、TAB、权限与PDF实际操作。
8. 保存本次生成的全部资源身份，按依赖清理并复查残留；API异常或断言失败也保留输入、实际值和清理结果。

首条接入先用可识别金额变化作消费探针：输入A → 正常消费/发布 → 读取A；追加符合源契约的输入B → 正常消费/发布 → 新读取B。根据独立差值核对源行、投影、generation与API。若金额没有进入某一层，先定位入口/筛选/水位/缓存，不用改写派生答案补齐。

旧基础设施有三个具体适配点：旧专用账户默认没有NT映射；部分用例直接写冻结视图；旧分钟路径使用专用snapshot引用、UUID批次ID和固定generation=1。它们能验证自己实际经过的查询计算，不能原样当作新版NT→分段→发布链已跑通。

按新接口契约逐端点校准参数：`X-Quant-Contract`不再参与路由选择；当前页面来源分支用`metric_source=prometheus`，但E05/E07等不接受该参数；`snapshot_id`、`generation`、`source_generation`语义不同。N02图窗from/to与指标metric_from/to分开，不把90天图窗当账号全历史统计范围。

清理器扩展到本次真实生成的资源：分段事实、检查点/代次、曲线、平仓重放分块、读取页、政策/周期/账单/归因/到账/凭证/outbox等，并核对本次身份和外部引用。共享namespace或共享generation不能整行删除其他账户结果；这类资源按正式维护方式处理，精确清理能力未绑定时保留为执行准备缺口。

继续使用现有`tests -> service -> api/db`分工；场景与输入放tests，流程编排放service，端点放api，SQL与实体访问放db，不新增架构层。
