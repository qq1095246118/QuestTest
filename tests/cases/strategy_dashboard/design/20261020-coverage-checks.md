# 分润模块测试完整性核查与证据约定（2026-10-20）

本文用于防止测试思路在细化、实现和执行过程中丢失需求、合并关键分支或扩大通过结论。它是本轮测试设计的核查规则，不是新的产品需求，也不表示相关场景已经实现或执行。

本轮采用用户已确认的产品、技术规则；不重新讨论已确认公式。本版范围为一个账户同一时刻运行一个策略，同策略可运行在多个账户，账户允许按切换记录依次运行 A→B→A。未来一个账户同时运行多个策略的讨论不纳入本版通过条件。

以下约束在本轮细化时保持一致：

- 账户和策略的收益率、仓位比例分别使用其已确认维度，不能为了统一测试而改成同一个公式。
- 策略归属区间依据切换记录，资金区间依据已确认的真实资金流规则；同一策略多账户运行时长按当前基线处理重叠区间。
- 日单位展示和分钟数据精度分别验证；不得由图表标签为“日”推断历史原始分钟数据可以丢弃。风险指标各自采用本轮技术基线指定的输入和采样口径，不能把所有指标强行套成同一种频率。
- 年化收益率按本轮在线基线验收：不足 7 天不计算；满足计算条件后的公式、恰好 7 天及时间边界引用当前基线。不得沿用旧材料中以固定最短天数替代实际时长的期望。
- 达到分润条件后冻结原账单并立即开启后继计费周期；之后的收款登记补充原账单，不再次重置后继利润，也不模拟真实出金。
- 不设计独立于当前基线的“登记→审核→清算”流程。下文“确认收款”指当前基线由有权商务完成的收款操作，不表示新增财务审核节点。
- 技术文档 7.1 的首次配置覆盖此前尚未计费的有效收益，已计费收益不能重复进入首次检测；配置和检测的适用时点以当前基线为准。
- 收款由技术文档 7.3 指定的商务执行，管理员不能绕过该资源归属限制。技术文档 7.6 的 24 小时收款要求及逾期人工跟进纳入测试，不新增自动停策略、出金或审核动作。
- 采集 300 秒、计费检测 60 秒、通知队列 10 秒是当前技术调度节奏，不是每个账户端到端完成的 SLA。时序证据分别记录输入就绪、任务运行和结果发布，不把相应数字直接用作逐账户完成时限。
- 具体 API 枚举、错误码、重试方式、可观察字段和未在本轮在线文档中核实的细节，在实现时引用当前基线并映射真实契约；本文件中的测试观察项不自动成为产品字段要求。

基线登记至少保留 `baseline_id、document_url、section、captured_at、document_version_or_snapshot、user_confirmation_ref、deployment_version、effective_scope`。没有可观察的文档版本号时保存快照引用，不编造版本号。

## 2. 覆盖总账与持续扩展

覆盖总账先逐条摘出文档要求，再展开数据、事件和页面分支；不能先确定一个目标用例数，再将其余内容压缩进已有编号。

| 层级 | 最小记录单位 | 必须保留的关系 |
| --- | --- | --- |
| 需求条款 | 一项可独立判断的业务行为、公式、字段或页面规则 | 原文定位 → 需求 ID |
| 测试分支 | 一个会改变预期、状态、参与集合或计算窗口的条件 | 需求 ID → 分支 ID |
| 场景 | 一套可以执行、具有确定数据和断言的操作时间线 | 分支 ID → 场景 ID → 数据集 ID |
| 实现 | 实际调用的测试入口、流程和来源路径 | 场景 ID → 执行器 → 经过的验证层 |
| 执行 | 本轮真实发生的一次验证 | 场景 ID → run_id → 分层结果 → 证据 |

建议总账字段：`requirement_id、source_section、baseline_id、branch_id、case_id、dataset_id、priority、subject、window、validation_layers、executor、design_status、execution_status、evidence_ref、gap_reason、supersedes、excluded_reason`。

维护时遵守以下规则：

1. 新增场景使用稳定 ID；改名不换 ID，改变业务含义时新建 ID 并保留替代关系。
2. 旧规则过期标记 `SUPERSEDED` 并指向新规则；不删除旧场景和历史执行证据，不把旧通过自动迁移到新规则。
3. 同一步骤可以复用或引用，但每个独立分支仍有自己的数据、期望和执行状态。
4. 一个场景验证多个字段时，逐字段保留断言结果；一个字段失败不能遮蔽其他字段未执行或缺源的事实。
5. 一个场景需要 API 和页面两层时，两层单独登记。API 通过、页面未验时不得整体显示全链路通过。
6. 自然样本不足、执行器缺失、环境阻断、产品失败分别记录，不靠删除场景或更换不满足条件的样本减少缺口。
7. 不适用分支必须写明当前基线依据；“太多”“后面再看”不能作为排除理由。
8. 每次新增或变更需求，回查受影响数据集、独立期望、执行器、UI 映射和回归集合；更新覆盖差异，不重写历史结果。

## 3. 完整性核查规则（20 项）

下表是设计检查项，不与业务场景数或通过数相加。

| 核查 ID | 检查内容 | 满足条件所需证据 |
| --- | --- | --- |
| CHK-01 | 原文逐条落点 | 每个适用条款至少关联一个分支；未设计条款单独列出 |
| CHK-02 | 场景反向有依据 | 每条场景能定位到当前规则；探索性观察标明观察范围，不冒充既定需求 |
| CHK-03 | 范围和旧规则隔离 | 单账户单策略限制明确；同时多策略、旧审核清算和旧公式都有过期/范围外说明 |
| CHK-04 | 字段和页面齐全 | 按页面、TAB、卡片、表格、曲线、详情和已定义导出逐项登记，不用“页面一致”概括全部字段 |
| CHK-05 | 身份和参与集合独立 | 账户、策略、交易所、运行状态、完整分页和历史关系有独立选集依据；预期集合不直接照抄待测汇总 |
| CHK-06 | 公式依赖完整 | 每项公式登记输入、单位、符号、窗口、分子/分母和聚合规则；账户与策略分别核对 |
| CHK-07 | 数值分支完整 | 对适用字段覆盖正、负、真零、极小值、大值、缺失与精度边界；不适用分支有理由 |
| CHK-08 | 时间边界完整 | 切换、资金流、查询、出账和收款等关键边界分别验证之前、等于、之后；日切、时区按当前基线处理 |
| CHK-09 | 分钟历史完整 | 峰谷、缺点、重复、乱序、迟到、冲突、未闭合数据分别有场景；日展示不能替代分钟路径验收 |
| CHK-10 | 风险和运行时长分开 | 对每项指标使用其已确认采样和样本条件；有效运行时长与页面日标签不混用；不足 7 天的年化不计算 |
| CHK-11 | 状态和事件完整 | 每个适用事件记录账单、后继周期、资金、TAB、权限和通知的影响；拒绝动作和重复动作也有断言 |
| CHK-12 | 金额快照不可混用 | 冻结应收、当前钱包、真实资金流、原账单实收、后继周期利润分别保存；收款不重复扣钱包或重置新收益 |
| CHK-13 | 独立期望可信 | 固定数据事先手算；自然数据从原始事实独立重算；不调用被测算法或读取最终聚合值生成 expected |
| CHK-14 | 注入路径声明真实 | 数据写入原始来源、采集后输入、读视图或最终结果的位置明确；没有经过的采集/计算/动作层不计覆盖 |
| CHK-15 | 数据代次可比 | 记录每项来源时间和发布代次；按实际依赖核对兼容性，不强制不同来源具有虚构的同一观测时刻；跨代有限重取不掩盖业务差异 |
| CHK-16 | 缺失与失败可区分 | 真零、完整空集合、来源缺失、估算/默认值、部分结果、请求失败和标旧值按当前契约分别验证 |
| CHK-17 | 写动作异常完整 | 对当前支持的出账/收款等动作覆盖合法、非法、重放、并发和超时恢复；不新增产品没有的操作入口 |
| CHK-18 | 权限两层检查 | 按当前角色和资源权限，分别检查页面操作及直接 API；读取、登记、详情和已定义下载/导出不越范围 |
| CHK-19 | 关键交叉不丢 | 第 6 节的关键组合都有场景引用；一般场景的抽样依据、未取组合和剩余风险可查询 |
| CHK-20 | 结果和缺口不夸大 | 登记数、离线数、API 数、页面数、端到端数分别统计；保留未实现、缺样本、阻断、失败和历史执行时间 |

## 4. 分润事件与状态核对表（22 项）

“未触发”“原账单未收/部分收/收足”“后继周期运行中”等名称是测试观察用语，不是要求服务端使用同名枚举。实际状态值在执行器实现时按当前 API 契约映射。

表中要求的输入、阈值、分润比例、有效收益和周期本金均引用当前产品/技术基线；本表只展开事件造成的状态和金额变化，不重定义主公式。没有明确合同的纠错、撤销、退款能力不擅自新增动作。

| 事件 ID | 前置与事件 | 原账单/应收核对 | 后继周期、资金和页面核对 |
| --- | --- | --- | --- |
| EVT-01 | 未设置门槛或按基线设为禁用值 | 不应因检测任务误创建分润账单 | 展示和历史仍按当前规则读取；禁用不等于业务数据消失 |
| EVT-02 | 有效配置下收益低于门槛 | 未生成本周期账单 | 当前计费周期按既定边界继续；不得只因页面刷新推进周期 |
| EVT-03 | 收益恰好达到门槛 | 生成一次账单，金额、比例、时点和来源快照按当前规则冻结 | 立即开启后继计费周期，记录关联关系；首次收款前的 TAB 可见性按基线核对 |
| EVT-04 | 一次观测跨越多个门槛档位 | 按当前规则生成一张账单，不能拆成多个门槛账单重复计费 | 后继周期只开启一次；不能把同一收益重复带入新周期 |
| EVT-05 | 同一触发被检测任务、重试或并发重复处理 | 一个业务触发结果；原冻结金额不重复增加 | 不重复开启后继周期或制造资金动作；核对业务结果而非只比较 HTTP 成功次数 |
| EVT-06 | 出账后发生新的盈利或亏损 | 原账单应收保持冻结值 | 新盈亏进入后继周期；分别核对钱包、当前周期收益和账户历史 |
| EVT-07 | 出账后发生真实入金/出金 | 原账单应收不随资金流改写 | 后继周期本金和钱包按真实资金流及当前公式变化；不能将资金流当成交易利润 |
| EVT-08 | 未收款时读取、刷新或切换日期 | 不新增账单、收款和应收 | 不因查询改变周期或业务起点；当前页筛选不改写账单固定边界 |
| EVT-09 | 有权商务登记首次有效部分收款 | 补入原账单，实收增加、待收减少，不能冒充收足 | 首次确认后的 TAB 按基线出现；后继利润不重置，钱包不因登记再次扣减 |
| EVT-10 | 有权商务一次收足 | 原账单实收与应收对应、待收按当前精度归零 | TAB 和结算展示起点按该账单触发时点；账户全历史保留 |
| EVT-11 | 多次有效收款逐步收足 | 每笔原始收款各计一次，累计不超过应收 | 每笔收款不重开周期或重复扣钱包；页面进度与同一账单分母一致 |
| EVT-12 | 收款带凭证或不带凭证 | 两条合法分支均可按当前流程登记，金额状态符合基线 | 凭证为可选，不新增必须审核节点；有凭证时按当前权限核对读取 |
| EVT-13 | 收款金额非法或累计超出应收 | 按当前契约拒绝，不增加实际收款或改变应收 | 不改变后继周期、TAB 起点及钱包；保留已成功的其他收款 |
| EVT-14 | 其他商务、非指定商务的管理员、无权限或失效会话提交收款 | 按当前角色/资源范围拒绝；管理员身份不能绕过指定商务归属；不能通过替换账户或账单 ID 越权 | 页面按钮和直接请求分别验证；失败请求没有金额与周期副作用 |
| EVT-15 | 同一收款请求重放或响应丢失后重试 | 最终只计一笔；先查询业务终态再按真实契约恢复 | 不重复登记、不重复通知或扣款；未知响应不能直接认定业务失败 |
| EVT-16 | 两个收款请求并发且合计可能超收 | 最终合法累计不超过应收；记录真实成功和拒绝结果 | 不能丢失已成功收款，不因两个客户端都曾读到待收而放行超额 |
| EVT-17 | 新账单已确认，之后旧账单晚收款 | 旧款只补旧单；新账单金额和收款不被挪用 | 结算页起点不因旧单晚到账向前回退；按基线核对最近已确认账单 |
| EVT-18 | 出账后切换策略、停止/重启账户 | 已有账单和收款按账户身份保留；不随当前策略重复制单 | 当前/历史参与集合、策略归属和有效区间分别核对；后继周期边界引用基线 |
| EVT-19 | 通知发送失败、重试或队列重启 | 已形成账单不因通知失败丢失或重复生成 | 核对当前通知模板、收件人、时点和去重；重试成功不能制造第二次业务触发 |
| EVT-20 | 关键来源缺失、部分失败、迟到修订或旧代次晚到 | 按当前基线判断是否可触发；不将未知收益当成完整达标依据；已冻结账单不静默改金额 | 缺失与真实零区分，恢复后正确发布；未定义修订动作时只记录观察与合同缺口，不发明退款/重开账流程 |
| EVT-21 | 首次配置前同时存在尚未计费收益与已计费收益 | 按技术文档 7.1 纳入尚未计费的有效收益，排除已计费收益；达到门槛时按当前规则形成一次账单 | 保存历史计费依据与首次检测输入，重复检测不能将已排除收益再次计费 |
| EVT-22 | 到达或超过技术文档 7.6 的 24 小时收款要求 | 按当前基线核对起算点、时间边界、实际收款及剩余待收；不得因逾期重复制单或改变冻结应收 | 商务人工跟进；不新增自动停策略、自动出金或独立审核；已收足账单不能因旧任务结果误标待跟进 |

事件检查至少同时保留 `account_id、bill_id、trigger_at、bill_snapshot_ref、period_before/after、due/received/remaining、wallet_before/after、real_flow_ids、actor、request_ref、tab_visible、tab_start_at`。无法通过某一层读取的字段应指向另一真实证据来源或记录观察缺口，不能由测试补出“实际值”。

## 5. 分钟历史、聚合、异常和权限的分支核对

本节是业务明细的展开清单，每行都应在场景总账中建立对应分支或给出不适用依据。表中的分支数不是已设计或已通过的用例数。

| 模块 | 需要逐项落点的分支 | 不能替代该验证的结果 |
| --- | --- | --- |
| 分钟历史与日展示 | 日内峰谷；首尾观测；缺中间点；重复同值；同刻冲突；乱序；迟到修订；未闭合末桶；采集中断恢复；跨日/时区边界 | 仅日末值相同不能证明分钟最大回撤正确；页面刻度为日不能证明分钟历史不存在 |
| 风险与运行时长 | 已确认的逐指标采样；最低样本；全平/全正/全负/混合；零分母；分钟峰谷；停机与重叠运行区间；年化不足 7 天不计算；满足条件后的边界 | 不同指标不能一律复制一套日收益或分钟收益；本地计算通过不代表真实来源被消费 |
| 策略切换与资金流 | A→B→A；停止后重启；持仓跨边界；事件在边界前/等于/后；同刻资金流；连续多笔资金流；重复切换记录；时段内无收益 | 只核对当前策略名称不能证明历史收益和分母归属正确 |
| 页面参与集合 | 一个策略多个账户；资金不等；正负收益抵消；运行/停止/未知；跨交易所；完整分页；筛选变化；重复关系；当前与历史集合 | 单页合计、两个 API 返回相同数字、同名对象截图都不能独立证明完整集合正确 |
| 页面字段聚合 | 每个字段分别登记求和/加权/最大值/重算等已确认规则；部分账户缺源；单指标查询与全指标查询；顺序不变性；分页不改变总量 | 不能把账户比例直接相加，不能因一个金额通过而推断其他比率通过 |
| 来源与发布 | 真零/缺字段/null/完整空集合；估算或业务默认及恢复；半批成功；旧代晚到；重复事实；来源撤回/修订仅按当前支持合同；发布/缓存失败恢复 | 写入期望最终值后读回、HTTP 200、缓存时间更新不能证明原始来源或计算正确 |
| 权限和资源范围 | 指定商务；其他商务；非指定商务的管理员；无权限；失效会话；替换账户/账单/凭证 ID；列表/详情/下载/导出范围（以当前基线支持为限） | 管理员身份不能代替指定商务归属；仅隐藏按钮不能证明 API 拒绝；仅拒绝写入不能证明详情读取未越权 |
| 页面显示与操作 | 单位/符号/精度；真实零与缺源；长文本/大数/极小数；曲线悬停；筛选/分页；刷新恢复；TAB 出现及起点 | 只检查响应或图表配置不能证明真实页面可读和交互正确 |

## 6. 必须展开的关键交叉组合（18 组）

这些是本轮测试设计要求的高风险组合，不是对产品新增功能。每组须关联至少一个满足其条件的业务场景；无法执行时保留缺口。一个数据集可以复用，但不能把一次执行同时冒充所有未实际发生的组合。

| 组合 ID | 交叉条件 | 主要判定点 |
| --- | --- | --- |
| CROSS-01 | 策略切换 × 入/出金 × 同一时间边界 | 收益和本金按各自已确认规则归属，无漏段、重段或重复本金 |
| CROSS-02 | A→B→A × 持仓/交易跨切换 × 账户历史 | 策略归属和账户全历史各自正确，不只按当前策略回填历史 |
| CROSS-03 | 同策略多账户 × 不等本金 × 正负收益 | 按真实分段输入独立重算，区分加总、权重和比例规则 |
| CROSS-04 | 多账户重叠运行 × 停止/重启 × 年化时长 | 有效运行时长与重叠区间按基线处理；不足 7 天不计算，满足条件后的边界按原文判定 |
| CROSS-05 | 分钟峰谷 × 日单位展示 × 当前/最大回撤 | 日内峰谷不能因展示抽样丢失；当前回撤和历史最大回撤分别核对 |
| CROSS-06 | 来源缺失/默认 × 页面汇总 × 恢复发布 | 部分/默认状态不伪装完整实测，恢复后数值和状态同步更新 |
| CROSS-07 | 运行/停止/未知 × 跨页 × 当前/历史 TAB | 预期集合来自完整独立来源，不因当前页或点击行改变统计范围 |
| CROSS-08 | 达标出账 × 新收益 × 未登记收款 | 原单冻结，后继周期已运行，新收益不并回旧单 |
| CROSS-09 | 达标出账 × 真实出金 × 收款登记 | 真实出金影响钱包/周期本金；登记只补原单，不重复扣钱包或清新利润 |
| CROSS-10 | 后继周期已再出账 × 新单先收 × 旧单晚收 | 收款各归原单，结算起点不因旧单晚收倒退 |
| CROSS-11 | 部分收款 × 并发登记 × 超收边界 | 每笔最多一次，最终累计不超应收，不丢失已成功记录 |
| CROSS-12 | 检测任务重放/重启 × 同一触发 × 通知重试 | 一个业务触发只生成一次账单和后继周期，通知失败不制造第二次触发 |
| CROSS-13 | 收款响应超时 × 服务端已成功/未成功 × 重试 | 先确定终态，按真实契约恢复，不因网络未知重复收款 |
| CROSS-14 | 切换/停止 × 已有待收账单 × 历史查询 | 待收和实收保留，归属、当前集合与历史集合不混淆 |
| CROSS-15 | 商务权限 × 替换账户/账单 ID × UI/API | 合法资源可操作，越权资源拒绝且无副作用；UI 和 API 证据分别保留 |
| CROSS-16 | 分页/筛选查询 × 新代发布 × 局部失败 | 同场景使用可比代次；有限重取记录原因；不能因跨代差异或缺源错误拼接完整汇总 |
| CROSS-17 | 24 小时收款边界 × 部分/足额收款 × 商务跟进 | 按技术文档 7.6 的时间口径判断；剩余待收与跟进对象正确，不制造自动停策略或资金动作 |
| CROSS-18 | 首次配置 × 尚未计费/已计费历史收益 × 重复检测 | 依技术文档 7.1 纳入未计费收益，排除已计费收益，首次和重试都不遗漏、不重复 |

一般场景可按等价类、边界值和风险选择代表组合，执行前登记 `dimensions、selected_values、selected_combinations、selection_reason、unselected_combinations、remaining_gap`。采用两两组合时只能声明相应维度的两两覆盖，不能宣称所有三维及以上组合已覆盖。

不能因某种组合已有一个成功例子，就去掉其他具有不同预期的失败、缺源、权限或时间边界分支。若发现新缺陷或新来源路径，应新增相应组合或回归，不修改旧记录制造“原本已覆盖”。

## 8. 设计、执行和结果状态

设计状态与执行状态分开记录，防止“已设计”被显示为“已通过”。以下状态名称为测试报告约定，不是产品状态。

| 状态 | 含义 | 不能据此声称 |
| --- | --- | --- |
| DESIGNED（已设计） | 有适用基线、数据、步骤和独立期望，尚未完成本次执行 | 业务已覆盖或环境已验证 |
| ADAPTER_REQUIRED（待实现） | 场景存在，但真实动作、来源消费、查询或页面执行器尚未接通 | 用离线替身或目录注册代表真实业务通过 |
| SAMPLE_GAP（样本缺口） | 当前执行路径可用，但没有满足该分支的自然样本或受控数据 | 使用不满足条件的样本替代后显示通过 |
| BLOCKED_ENV（环境阻断） | 认证、网络、部署、依赖或测试基础设施阻断，未完成所需业务断言 | 产品计算失败，或场景已验证通过 |
| PASSED（通过） | 在记录的版本、数据、层级和时点完成全部适用断言 | 未经过的层级、未取样组合或其他版本自动通过 |
| FAILED（失败） | 满足有效前置且输入/基线可比时，实际业务结果与当前独立期望不符 | 所有关联用例都自动失败，或必然是某个具体实现根因 |

另保留 `NOT_RUN`（本轮未执行）、`SUPERSEDED`（旧规则已替代）、`OUT_OF_SCOPE`（有依据的范围外）标记。主动关闭 live、只做目录检查、只执行离线校验应记为未执行相应业务层，不能归为自然样本缺口。

一个场景可以同时具有 `design_status=ADAPTER_REQUIRED` 和某个历史版本的执行记录；本轮报告只依据本轮状态，不覆盖历史。失败后修正测试期望必须说明当前基线依据并保留原失败；修复后通过生成新执行记录。

若某字段通过、其他字段缺源，保留逐字段结果及整体未完成范围，不能把整条用例归为完整通过。若 API 通过但页面未执行，API 层可记通过，全链路仍为未完成。

## 9. 交付前的覆盖报告

每次生成设计或执行报告至少输出以下互不混淆的计数：

1. 适用需求条款总数、已映射条款数、未映射条款清单；条款映射率只表示设计追踪，不表示运行通过率。
2. 测试分支总数、已设计分支数、未设计分支、明确不适用分支及依据。
3. 稳定业务场景数、参数化数据实例数、断言数分别列出；不能相加当成新的业务场景数。
4. 已有真实执行器、待实现、样本缺口、环境阻断、未执行、通过、失败分别列出。
5. 原始来源、公式、发布/API、业务动作、UI、全链路各层结果；离线校验单列。
6. 18 组关键交叉组合的场景映射及剩余缺口；一般场景抽样的实际组合范围。
7. 本轮执行和历史执行的日期、版本分别列出；旧结果不重标为本轮回归。
8. 失败归并后的缺陷数与受影响场景数分别列出；一个根因影响多个字段不重复制造缺陷数量。

完整性报告应显示未完成项。零遗漏只能在已登记的适用基线范围内，经过逐条映射和分支核对后描述，不能承诺对未知需求或所有输入的绝对穷尽。
